# post-lab requirements

Status: requirements questions resolved as D1–D5; solution decisions D6 onwards (2026-10-27). Collected from `CLAUDE.md`, `next-session.md` and the discussion that aborted `docs/plan.md`. Lists **what** post-lab must do, not how.
## Purpose

- R1. A labs tool for storyboarding and data analysis for blog posts.
- R2. Installed into a host repo (e.g. a blog post's repo) and used from there. Every board is tied to the codebase it is installed in.
- R3. The blog framework of the host repo doesn't matter; the post is an output of the analysis.

## Canvas

- R4. A Miro-like spatial board for storyboarding.
- R5. Freehand drawing.
- R6. Shapes, frames (grouping areas) and arrows/connectors between items.
- R6a. Content items are styled with a small token set: colour from a fixed palette (~8 colours), size S/M/L, text alignment. Clean, non-hand-drawn look. The UI offers no style options for content items beyond the tokens. Shapes are content items and use the tokens (D7). Opaque freehand strokes may use their own styling (D2).
- R7. Text boxes and stickies, usable without any code cells. Their text displays as typed; markdown is not rendered (D3).
- R8. Multiple boards per host repo.

## Moodboard

- R9. Images can be dropped or pasted onto a board.
- R10. Link embeds for any URL. Known providers (e.g. YouTube) can play inline; other URLs need at least a preview.
- R11. Font specimens and colour swatches are not needed.
- R11a. Board export (PNG/SVG) is not needed (D4).

## Code cells (notebook feel)

- R12. A cell runs code from the host repo and shows its data/analysis output on the canvas.
- R13. Cells work with any language (Python is the usual case). Code lives in real script files in the host repo, never inside the board.
- R14. Cells are stateless: they talk to post-lab only through the files they write and their stdout.
- R15. Outputs render by type: images, tables (CSV/JSON), charts (Vega-Lite), interactive HTML (e.g. Plotly), markdown, stdout.
- R16. Outputs can be re-generated by re-running the cell.
- R17. Outputs are committed to git, so a board shows its results without re-running anything.

## Storage

- R18. All data lives as files in the host repo. No database, cloud storage, or user-level/global state.
- R19. Everything is versioned with git alongside the code it describes, and diffs are readable.
- R20. AI-native: cheap and fast for an agent to read and write directly (plain text, small files, no need to load a whole board to change one item). Applies to content items: notes/stickies, text, shapes, images, link embeds, cells, frames and connectors. Freehand strokes may be stored in an opaque format (D1, D7).
- R21. Hand-editable in a text editor, with the same scope as R20.
- R22. Edits made by hand or by an AI agent show up in the open UI.
- R23. Images are stored as files in the repo, not embedded in another file.

## AI access

- R24. AI agents work on boards only by editing files. There is no post-lab CLI for editing boards and no MCP server.
- R25. The host repo contains a short guide explaining the file format so agents can edit boards correctly.

## Distribution and environment

- R26. Added to an existing repo and started with one command. Node is the only prerequisite.
- R27. The tool's own code is kept separate from the board data it writes into the host repo.
- R28. Permissively licensed dependencies only (MIT, ISC, BSD, Apache-2.0). tldraw is excluded: its licence is source-available and needs a key or watermark in production.
- R29. Running a cell executes code with the user's privileges. Other local web pages must not be able to trigger it. post-lab is only used locally, by one user (D9).

## Engineering constraints (user's global rules)

- R30. Use established libraries rather than building from scratch.
- R31. No fallbacks and no backward-compatibility code.
- R32. Cyclomatic complexity under 10, enforced by the linter.
- R33. Styling through the framework's theming (shadcn/Tailwind/Radix/Lucide), never hardcoded.

## Decisions

- D1 (Q1). Why not plain Excalidraw? Plain Excalidraw already covers R4–R7, R9 and part of R10. **Decision: all three differentiators are required — cells (R12–R17), agent/hand-editable storage (R20–R21) and images as files (R23) — with agent/hand-editability scoped to content items.** Notes/stickies, text, images, link embeds, cells, frames and connectors must be plain-text editable. Freehand strokes and shapes may be stored opaquely.
  - Rationale: the user wants images and running code, and AI-native storage is a hard requirement. Freehand stroke point lists are not meaningfully readable or editable as text, and a full two-way mapping of every element and style was the main cost that sank `docs/plan.md`. Scoping editability to content keeps agents able to build and edit storyboards while shrinking the mapping.
  - Facts considered: plain `.excalidraw` stores images as base64 inside one JSON scene. The Obsidian Excalidraw plugin already saves pasted images as separate vault files and stores drawings in markdown files, so R23 alone would not justify a new tool. JSON Canvas (Obsidian's MIT-licensed open format, spec 1.0, 2024) is plain JSON with text/file/link/group nodes and edges that reference files, but has no freehand drawing.

- D2 (Q2). How much canvas fidelity is required? **Decision: content items persist a small token set (palette colour, size S/M/L, text alignment) with a clean, non-hand-drawn look. Opaque strokes and shapes keep whatever styling the canvas offers.** See R6a.
  - Rationale: each persisted style field adds to the file format, the mapping and what agents must get right. Named tokens keep item files short and let agents style items without guessing hex values. Opaque elements cost nothing to map (D1), so restricting them gains nothing.
  - Facts considered: an Excalidraw element carries about ten style fields (stroke and background colour, fill style, stroke width and style, roughness, opacity, roundness, font family and size, alignment).

- D3 (Q3). Must markdown in notes and text render on the canvas? **Decision: no. Notes/stickies and text show raw text; markdown renders only in cell outputs (R15).** See R7.
  - Rationale: keeps notes as native, cheap canvas items on any canvas library and leaves the canvas choice open.
  - Facts considered: Excalidraw text elements are plain text only; rendering markdown there would mean custom HTML embeddables, losing native inline editing, wrapping and canvas export. HTML-node canvases (e.g. React Flow, JSON Canvas renderers) render markdown easily.

- D4 (Q4). Must a board export (PNG/SVG) include cell outputs? **Decision: board export is not a requirement.** See R11a.
  - Rationale: the blog post, not the board, is the deliverable. Outputs are already repo files (R17) the post can use directly, and boards are shared by running post-lab or by screenshot.
  - Facts considered: Excalidraw's export draws embeddables as placeholders, not their content. Sandboxed HTML outputs (e.g. Plotly) cannot be rasterised by a canvas exporter without a headless browser (e.g. Playwright), which would add a prerequisite beyond Node (R26).

- D5 (Q5). Which differentiator should be proven first with a spike? **Decision: no spike. D1–D4 set the direction; proceed to solution choices directly.**
  - Rationale: the user is committed to this direction and does not need a spike to justify it.

- D6. Canvas library. **Decision: React Flow (`@xyflow/react`) as the canvas, with freehand drawing added using perfect-freehand.** Notes/stickies, text, cells, images, link embeds and shapes are custom React nodes styled with Tailwind/shadcn. Freehand strokes are perfect-freehand SVG nodes. Frames use React Flow sub flows (parent nodes). Connectors are React Flow edges, so they always join two items.
  - Rationale: items render directly from their files as our own components, with no foreign scene to map to and from (the cost that sank `docs/plan.md`). React Flow handles the hard interaction work (pan/zoom, select, drag, resize via NodeResizer, grouping, edges), which fits R30. Cells are ordinary HTML nodes, not embeddables.
  - Trade-offs accepted: drawing UX is simpler than Excalidraw's; freehand and shape tools are ours to build; no free-floating arrows.
  - Facts considered: React Flow is MIT; its d3 dependencies are ISC (allowed by R28). It renders its own wrapper DOM; `base.css` holds the required styles and nodes take any styling. Its freehand example is a paid Pro example, so it can't be copied. The vanilla core `@xyflow/system` isn't intended for use outside React Flow and Svelte Flow. Rejected: Excalidraw (keeps the element mapping and its styling UI), a fully custom canvas (most code to own, weakest fit with R30), Quickdraw (self-described as young, no frames or custom shapes, images stored in the document).

- D7. Storage format. **Decision:**
  - Each content item is its own markdown file with YAML frontmatter, `items/<id>.md`. The frontmatter holds type, position, size, style tokens (D2), `frame`, and cell settings. The body holds the item's text; non-text items (images, cells) have an empty or descriptive body. Files are split into frontmatter and body by post-lab itself and parsed with `yaml`, not gray-matter.
  - Freehand strokes for a board live in one `strokes.json`.
  - Each connector is its own item file (type connector, with `from`, `to` and an optional label).
  - Shapes are item files like notes, styled with tokens. With React Flow they are our own components, so storing them as content costs nothing; this narrows D1's opaque scope to freehand strokes only.
  - Item IDs, which are also the filenames, are short random IDs. No clash handling or rename logic is needed, and the ID never goes stale when an item's text changes.
  - Layout in the host repo:
    ```
    post-lab/
      README.md                 # agent/human guide to the format (R25)
      boards/<slug>/
        items/<id>.md
        strokes.json
        assets/<file>           # images; an image item's frontmatter has `src: assets/<file>`
        outputs/<cell-id>/      # files a cell writes, committed (R17)
    ```
  - No board metadata file: a board's name is its folder slug, and no requirement needs more. Images and outputs stay inside their board, so a board is self-contained and deleting it leaves nothing behind. Pasted images are saved as `<item-id>.<ext>`; agents may add images under any filename and point `src` at them.
  - Items inside a frame store `frame: <id>` and positions relative to the frame, matching React Flow sub flows.
  - Rationale: one file per item satisfies R20 (change one item without loading the board) and keeps agent and UI edits on different files, so fewer git conflicts. A markdown body needs no YAML escaping for text, which makes it the easiest form for agents and humans to edit. Strokes are opaque (D1) and noisy, so one file keeps the items folder readable. Connector files mean deleting or editing a connector never touches another item. Relative positions make moving a frame a single file edit.
  - Facts considered: gray-matter's built-in `---js` engine evals the file, and its `stringify` breaks byte-for-byte round trips (from `docs/plan.md`). JSON Canvas was rejected: one file per board breaks R20 and causes more conflicts.

- D8. Live sync. **Decision: a local Node server (Hono) watches `post-lab/boards/` with chokidar and pushes changed items to the UI over Server-Sent Events. The UI saves items with HTTP PUT. Last write wins: the file on disk is the truth, incoming changes replace the item in the UI, and the next UI save overwrites the file.**
  - Rationale: changes only need to flow from server to UI, so SSE is enough. Browsers' EventSource reconnects on its own, so no reconnecting-socket library is needed, and Hono has built-in `streamSSE`. A clash between a UI edit and a disk edit of the same item is rare, costs one edit, and git keeps the history.
  - Facts considered: chokidar handles editors' atomic saves. In chokidar 6, `unlink` is not delayed by `awaitWriteFinish`, so re-read the file from disk at refresh time rather than trusting the event type. Echo suppression worked by updating the in-memory store before writing and comparing content hashes (both from `docs/plan.md`). Rejected: WebSocket (two-way channel plus a reconnect library for a one-way flow), polling (laggy, can lose edits).

- D9. Cell execution and security. **Decision:**
  - A cell's frontmatter has `command`, a shell string (e.g. `uv run analysis/churn.py`), and an optional `cwd` relative to the host repo root.
  - Cells run only when the user clicks Run in the UI, never on file changes.
  - A run empties `outputs/<cell-id>/`, sets `$POST_LAB_OUT` to it, and runs the command via execa. stdout is saved there as `stdout.txt`, so it is committed with the other outputs (R17). stderr and the exit code are shown when a run fails.
  - The server binds to 127.0.0.1 and rejects any request whose Host header is not its own, and any state-changing request whose Origin is not its own. GET routes have no side effects. There is no sign-in, token or session cookie.
  - Rationale: a shell string lets cells use pipes, globs and `&&`, and agents write it naturally. Running only on a click means an agent's edit to a cell file never executes code by itself. Host/Origin checks block cross-site requests and DNS rebinding from other web pages in the user's own browser (R29). Browsers let any page send GETs but not read the replies, so GETs must not change anything.
  - Revised 2026-11-02: M1 first shipped a one-time launch token swapped for a session cookie. post-lab is only ever used locally by one user, so the token only guarded against other users on a shared machine, or processes that can reach localhost but can't already run code as the user. That was not worth a sign-in link and a new one on every dev restart, so it was removed.
  - Facts considered: Vite's string proxy shorthand sets `changeOrigin`, which rewrites Host; the dev proxy must use the object form with `changeOrigin: false`. Rejected: argv-list commands (no shell features), auto re-run on change (would execute agent-written code without a click).

- D10. Distribution and build. **Decision: a published npm package with a `post-lab` bin, run with `npx post-lab` from the host repo root. Host repos with a package.json may add it as a devDependency to pin the version. The React + TypeScript frontend is built with Vite at publish time and served by the Hono server; in development the Vite dev server proxies `/api`.**
  - Rationale: works in host repos without a package.json (e.g. Python-only analysis repos) and still allows pinning. Node stays the only prerequisite (R26). Rejected: requiring a devDependency (every host repo would need a package.json).

- D11. Agent guide. **Decision: post-lab owns `post-lab/README.md` and rewrites it on every launch. The file says at the top that it is generated and that hand edits are lost.**
  - Rationale: the guide always matches the running version's format (R25). Rejected: writing it once (goes stale when the format changes), a separate generated `FORMAT.md` beside a user-owned README (two files for agents to find).

- D12. Output renderers. **Decision: every file in `outputs/<cell-id>/` renders, sorted by name, with the renderer chosen by extension alone:**
  - `.png`, `.jpg`, `.gif`, `.webp`, `.svg`: images.
  - `.csv`, and `.json` holding an array of objects: tables with TanStack Table. A `.json` that is not an array of objects shows an error.
  - `.vl.json`: Vega-Lite charts with vega-embed.
  - `.html`: an iframe sandboxed with `allow-scripts` only, so it has an opaque origin and cannot reach post-lab's API.
  - `.md`: react-markdown.
  - `stdout.txt`: monospace text.
  - Any other extension: a link to the file.
  - Rationale: covers every type in R15 with established libraries, and scripts and agents know exactly what to write. Rejected: a per-cell manifest file (more control over order and titles, but every script must write it).
  - Facts considered: TanStack Table and react-markdown are MIT; vega-embed is BSD-3-Clause (allowed by R28).

- D13. Validation. **Decision: zod 4 schemas validate item files when they are read. The field reference in the agent guide (D11) is generated from the same schemas with `z.toJSONSchema()`.**
  - Rationale: zod is MIT and the most established schema library. Generating the guide from the schemas means the docs and the code can't drift. Rejected: valibot (smaller, but less widely used, and JSON Schema export needs a separate package).

- D14. Dev tooling. **Decision: pnpm, Vitest, ESLint with typescript-eslint (`complexity` max 10, enforcing R32), and Prettier.**
  - Facts considered: pnpm 12 blocks dependency build scripts until approved (`allowBuilds` in `pnpm-workspace.yaml`, needed for esbuild) and enforces a minimum release age. TypeScript 6 defaults `types` to `[]`, so each tsconfig must list `node` or `vite/client`. shadcn's generated components fail `react-refresh/only-export-components` and a no-inline-`style` rule, so those rules must exclude `components/ui/**` (all from `docs/plan.md`).
